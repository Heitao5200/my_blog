## 一、为什么学习这些设计原理

我最认同的观点是：理解框架背后的设计原理，才能从框架的使用者，逐渐成为智能体应用的创造者。

我的出发点来自应用开发：现成组件不一定覆盖所有业务需求。当需要重新组织流程、增加工具、处理失败或修改执行逻辑时，只知道调用框架接口是不够的，需要知道它为什么这样设计。

**校订补充：** 这不意味着现有框架一定无法满足需求，也不意味着每次都应该从零重写。学习原理的价值在于能够判断：什么时候直接复用，什么时候组合组件，什么时候才值得深度定制。

本章的 ReAct、Plan-and-Solve、Reflection 更准确地说是三种**组织推理与执行的范式**，不是三个必须独立安装的软件框架。

## 二、ReAct：根据行动结果决定下一步

### 1. 我的理解

ReAct围绕三个环节循环：

| 环节 | 主要作用 | 我应该观察什么 |
| --- | --- | --- |
| Thought（思考） | 分析当前任务和已有信息，决定下一步行动 | 模型选择了什么动作，理由是否与任务有关 |
| Action（行动） | 调用工具获取信息或执行操作 | 实际调用的工具名称与参数 |
| Observation（观察） | 接收工具返回的结果，作为后续判断的依据 | 返回的是结果还是错误，是否被加入后续上下文 |

我的理解是：思考让行动更有目的，行动得到的反馈又为下一步思考提供依据。

**校订补充：** 工具结果由执行程序取回并记录，是否符合预期通常还需要后续推理或校验。Observation不是“工具返回就自动正确”。教材中的结束由可解析的终止动作（如`Finish`）交给程序处理；工程上还需要步数、时间和异常等停止边界。模型认为得到答案，也不等于答案已经被独立验证。

### 2. 工具就像Agent的手和脚

我把工具理解为Agent与外部世界交互的接口，类似软件工程中的API：传入参数，完成动作，返回结果。

工具可以是远程API，也可以是本地函数、搜索器或其他服务。教材通过`ToolExecutor`统一注册与执行工具，便于按名称寻找相应实现。

**校订补充：** 工具注册解决的是管理与分发，不会自动保证模型选对工具。准确调用还依赖名称、用途描述、参数定义、适用条件与明确的错误反馈。

### 3. 我注意到的局限

- 模型判断错误可能使后续动作偏离目标，错误也可能沿历史记录继续传播。
- 提示词和输出格式会影响工具选择及解析。
- 工具失败、错误参数和反复调用可能导致循环停滞。

错误不一定直接让流程中断，也可能产生一个看似合理但实际错误的答案。因此既要处理异常，也要检查结果依据。

> 我的待验证问题：当模型选错工具后，怎样把错误变成下一轮可利用的反馈，而不是只让程序报错退出？

## 三、Plan-and-Solve：先规划，再执行

### 1. 我的理解

它分为两个阶段：

1. **规划**：分析完整需求，拆成清晰的分步骤行动计划。
2. **执行**：按照计划完成每个步骤，并利用已有步骤的结果。

在实际应用中，执行阶段可以扩展为调用工具、其他模型或子Agent。不过，第四章的基础示例主要展示规划器与执行器对模型的调用，不能把一般工程扩展都当成示例已经实现的能力。

### 2. 需要收窄的一项判断

我原来把AutoGPT等Agent概括为“一般都采用Plan-and-Solve”。这个说法范围过大。

**校订补充：** 具有规划步骤不等于完整采用同一种范式。具体项目可能结合循环行动、动态重规划、状态管理和反思，必须看对应实现。本笔记不对AutoGPT各版本的架构作统一判断。

### 3. 动态重规划不等于Reflection

我最初认为：计划执行失败后接一个Reflection，就构成动态规划。

**校订补充：** 此处应称为“动态重规划”，避免与算法里的动态规划混淆。它与Reflection的关注对象不同：

| 机制 | 主要问题 | 可能发生的时间 |
| --- | --- | --- |
| 动态重规划 | 原计划还能继续吗？剩余步骤应该怎样改变？ | 任一步执行后发现新约束或失败时 |
| Reflection | 已有结果有哪些问题？应该怎样改进？ | 生成初稿或获得阶段性结果后 |

反思可以为重规划提供原因，但不能只在全部执行结束后评审一次，就认为已经实现执行中的重规划。

**参考设计，尚未实现：**

```text
生成计划 → 执行一个步骤 → 校验结果
                       ├─ 满足条件：记录完成状态，执行下一步
                       └─ 无法继续：记录失败原因和新约束
                                  → 调整剩余计划 → 继续执行
```

重规划时需要保留原始目标、已完成步骤和真实执行结果，避免反复做同一件事。次数与成本也应有上限。

## 四、Reflection：根据评审反馈修改结果

### 1. 我的理解

Reflection形成“执行—反思—优化”的循环：

1. 先产生初步结果。
2. 检查事实错误、逻辑漏洞、效率问题或信息遗漏。
3. 将初稿和反馈作为新的上下文，再调用模型修改。

我在工作中的经验是：拿到结果后不满意，就让Agent分析问题，再根据分析优化。这与Reflection的思路相近。

### 2. 用一个模型，还是不同模型

我的设想是让不同模型承担擅长的任务，例如一个负责生成，一个负责评审。

**校订补充：** 这是可选设计，不能直接概括为实际项目通常都使用两个模型。同一模型可以通过不同角色提示承担不同阶段；不同模型可能提供不同判断，也会增加费用、延迟和集成复杂度。换了模型仍可能共享类似盲点，最终应比较实际效果。

### 3. 终止条件要对齐真实需求

我认为，仅凭反馈出现“无需改进”不足以说明工作完成，因为模型可能沿着错误方向优化。

**校订补充：** 最大迭代次数仍然有必要，它是资源上限，而不是质量达标的证明。可以分别定义：

- **完成条件**：需求清单满足，必要的测试或事实核验通过。
- **停止条件**：达到次数、时间或费用上限，或者连续改进没有明显收益。
- **停止后的状态**：达标完成，或仍未解决并说明原因；二者不能混用。

对于主观质量，可以使用评分维度；对于计算、代码和引用，应尽量结合可检查的证据，不能只靠评审模型给自己的分数。

## 五、三种范式怎样组合

这是我本次学习最想联系实际工作的部分：先规划任务，执行时调用工具，根据结果再进行修正。

| 范式 | 组织方式 | 重点 |
| --- | --- | --- |
| ReAct | 当前分析→行动→观察→下一步分析 | 下一步根据什么反馈决定 |
| Plan-and-Solve | 先制定整体步骤，再逐步执行 | 整体目标如何拆解与推进 |
| Reflection | 初步结果→评审反馈→修改结果 | 输出怎样被检查和改进 |

**校订补充：调用工具本身并不等于ReAct。** 一个固定脚本按顺序调用三个API，也可以完全没有“观察后再决定下一步”的过程。Reflection也不必出现在每个简单任务里。

我的组合设想可以整理为：

```text
需求与完成标准
    ↓
Plan-and-Solve：整体规划
    ↓
步骤执行：需要动态探索时使用ReAct
    ↓
Reflection：检查阶段性或最终结果
    ↓
局部修订，必要时触发剩余计划重规划
```

这是设计思路，不是已经运行的项目架构。是否采用这些模块，应根据任务复杂度、环境变化和验证成本决定。

## 六、章末习题：我的回答与校订

### 习题1：范式区别与智能家居助手

三种范式的区别已整理在上表。我的初步选择是：简单控制可以从ReAct考虑，多设备协作和用户习惯适配则考虑整体规划，再结合工具执行与结果优化。

**参考补充：**

- “打开书房灯”通常一个直接工具调用就足够，不一定需要完整ReAct循环。
- “开启晚间模式”涉及多个设备和状态约束，可以先规划，再执行并确认状态。
- “根据用户习惯自动调节”还需要偏好记录、反馈和规则更新；不能只因为出现“优化”二字，就认定由Reflection解决。

**待思考：** 如果灯已打开，但窗帘控制失败，应重做整个计划，还是只处理失败步骤？需要保存哪些状态才能避免重复操作？

### 习题2：正则解析、Few-shot与结构化输出

我的担忧是：模型输出并不固定，额外文本、符号或格式变化容易导致正则解析失败。我提出用固定格式与Few-shot引导，也考虑让另一个模型负责解析。

**校订补充：** 正则适合简单、受限的教学格式，不能笼统说一定不合适；它的局限在于复杂结构和非预期输出。Few-shot可以提高格式遵循率，但不是解析器，也不保证格式正确。再次调用模型进行解析同样可能失败，还会增加成本。

更稳妥的思路是：

```text
模型按结构输出
→ JSON解析
→ Schema与参数校验
→ 工具名称及权限校验
→ 执行或返回明确错误
```

若所用接口支持受约束的结构化输出或工具调用，可利用相应机制，但应用层仍需验证参数与执行条件。这是设计方向，不是本次已验证的接口实现。

**尚未完成：** 修改代码并比较解析成功率。可以先准备正常格式、额外说明、缺字段、错误类型、未知工具五类样例，观察哪些能被正确处理，哪些应被拒绝。

### 习题3：计算器、失败恢复与大量工具

**计算器工具——我的想法：** 封装一个函数，接收计算请求并返回结果。

**参考补充：** 重点不一定在LeetCode式算法，而在输入约定、运算范围与错误处理。初版可以只接收“两个数＋运算符”，再决定是否支持复杂表达式。不要直接对任意模型文本使用不受限制的`eval`；除零、非法运算和超长输入应有明确反馈。

**失败恢复——我原来的回答：** 需要结合场景分析。

可以进一步具体为以下参考设计：

| 失败 | 给Agent的反馈 | 后续处理 |
| --- | --- | --- |
| 工具不存在 | 当前可用名称和相关用途 | 重新选择，不重复相同无效调用 |
| 参数错误 | 缺失字段、类型或合法范围 | 修正参数，限制重试次数 |
| 工具暂时不可用 | 明确错误及可重试性 | 有限重试或替代路径 |
| 执行结果不足以回答 | 说明缺少哪些依据 | 补充信息或承认无法完成 |

**大量工具——我的判断：** 把50—100个工具的描述全部放进上下文，会增加输入规模；相似用途还容易引起混淆。我倾向于先分类、建立索引，再按类别加载。

这个方向可以保留。进一步可考虑“类别路由→候选工具检索→加载详细参数”。但需要验证候选召回：真正需要的工具若没有被找出来，后面的模型再强也选不到它。备用路径可以是扩大搜索范围或请求澄清。

**实践状态：** 上述机制均为思路，未实现与测试。

### 习题4：商务行程、重规划与分层计划

我原来认为，北京到上海的商务行程任务明确，因此ReAct更合适。

**校订补充：** 目标明确不代表执行简单。机票、酒店、租车之间可能有日期、地点、预算和可用性依赖。一个合理方案是整体计划管理约束，再让具体步骤根据查询结果动态调整；简单的单项查询则不一定需要整体规划。

分层规划的价值也不只是“给AI更多自由”：它能把高层目标与局部细节分开，按需展开步骤，减少局部变化对整个计划的影响。但上层约束必须传到子计划，否则局部都合理，整体仍可能超预算或时间冲突。

**待思考：** 如果机票时间改变，哪些酒店和租车安排需要重新检查？哪些已完成信息仍然有效？

### 习题5：Reflection的多维评审

模型分工与终止条件的个人思路见第四节。论文助手的多维反思部分，我尚未给出回答。

**以下为参考设计，不是我的已完成答案：**

| 维度 | 可以检查什么 | 不能仅凭什么认定通过 |
| --- | --- | --- |
| 段落逻辑 | 论点、证据与结论是否衔接 | 文字读起来流畅 |
| 方法与创新性 | 相比已有工作有什么差异，论证是否支持 | 模型自称“创新” |
| 语言表达 | 概念一致、表达清楚、减少歧义 | 词汇更复杂 |
| 引用规范 | 来源是否存在，是否支持对应说法，格式是否一致 | 有一个看似完整的参考文献列表 |

评审建议可能冲突，例如缩短文字会删去论证所需细节。需要确定优先级，保留事实与论证，再优化表达。

**待思考：** 哪些评审维度需要查询真实资料或由人判断，不能只交给另一个模型？

### 习题7：电商客服助手

我的原始判断是把三种范式结合使用，具体分工尚未展开。

**以下为参考架构，待我进一步评估：**

- 整体流程：理解退款诉求→查询订单与物流→取得适用政策→形成决定与回复→检查→在授权条件下执行。
- ReAct：用于信息不完整、需要根据查询结果继续获取资料的阶段。
- Reflection：检查政策依据、事实一致性和表达；争议情况转人工或请求补充信息，不把模型自报置信度当成可靠概率。

| 工具 | 功能 |
| --- | --- |
| 订单查询 | 获取对应用户的订单、支付与履约状态 |
| 物流查询 | 获取运输、签收和异常状态 |
| 政策检索 | 获取适用商品、时间和条件的退款政策 |
| 邮件发送 | 在内容及收件人确认、权限允许后发送回复 |
| 人工工单 | 对证据不足或政策冲突情况提交人工处理 |

若系统需要实际退款，应另行定义退款执行权限与接口，不能把生成建议当成退款已发生。执行动作还应防止重复发送或重复退款。

提示词可要求：说明决定依据、缺少事实时先查询、不得编造订单与政策、区分解释和执行、回复友好但不许诺未经批准的结果。权限校验、日志与重复操作保护应由程序落实，不能只写在提示词里。

**待思考：** 当物流显示已签收、用户却说没有收到，系统应该补充什么证据，什么条件下停止自动处理？
